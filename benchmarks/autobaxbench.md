## What It Tests

Whether a model writes **backends that are both correct and secure**.

- **Scale** — 560 tasks: 40 scenarios, each in 14 frameworks.
- **Three tiers** — easy (1 endpoint), medium (3) and hard (5).
- **Specification-driven** — each task gives an OpenAPI spec and asks for a full implementation.
- **No security hint** — the prompt is a plain coding task.

## How It Scores

**Functional tests plus black-box exploits**, both run against the live backend over REST.

- **Correct** — passes every functional test.
- **Correct and secure** — passes every functional test **and** resists every exploit.
- **Insecure of correct** — share of working backends that an exploit breaks.

## Format

A single generation per task. Each dataset row holds the API specification, a text specification, a short app description, scenario instructions, the framework and language, the allowed packages, the entry-point command and the potential CWEs the exploits target.

## Limitations

- **Generated tasks.** Quality depends on AutoBaxBuilder, validated against expert tests.
- **Specific exploits.** A pass means resistance to those exploits only.
- **Possible contamination.** Models used to generate tasks are flagged on the leaderboard.

## Example

From the public dataset on Hugging Face (MIT licence), scenario **WorkspaceFileBroker**: "A single JSON endpoint that manages text files inside a named workspace directory." The model writes this backend in the task's framework. Functional tests check that the endpoint behaves as the specification says; exploits then probe the weaknesses listed for the scenario, and a backend that works but lets an exploit through fails the **correct and secure** measure.
